| **Authorization & Access Control** (*Complete if introducing or modifying REST APIs)* |  |
| **Authentication**: Is authentication required for all exposed API endpoints? | Yes. Every control-plane endpoint requires a valid OAuth2 bearer token. The gateway management API requires its existing bearer-token mechanism. The proxied WebSocket connections themselves can additionally be protected by configurable handshake-level authentication policies (API key, JWT, OAuth2/opaque token, basic auth), enforced before the connection is accepted. |
| **Authentication Mechanism:** How is authentication enforced? | OAuth2 bearer tokens for control-plane endpoints, the same mechanism already used for every other artifact kind; the existing bearer-token mechanism for the gateway management API; configurable handshake-level auth policies for the proxied connections. |
| **Privilege Level Defined:** What privilege level is required for the endpoints? (Admin, Publisher, Subscriber, Internal/System, Anonymous) | Publisher-level for create/manage/deploy operations; Subscriber-level for read/discovery and try-it; Internal/System for the gateway-management-API surface and the control-plane-to-gateway synchronization channel. Exact role names beyond these categories: NOT ANSWERED. |
| **Least Privilege Enforcement:** Is access restricted to the minimum required privilege? (Lower-privileged roles must NOT gain unintended access.) | Yes. Dedicated scopes (`ap:websocket_api:manage`, `ap:websocket_api:read`, `ap:websocket_api:deployment:manage`, `ap:websocket_api:deployment:read`) are checked per operation; a caller holding only the read scope cannot create, update, or deploy. |
| **Resource Ownership Check (BOLA / IDOR):** When accessing a resource using an ID in the URL, does the system verify that the authenticated user has permission to access that specific resource? *(Example: Preventing User A from accessing another user's order via `/api/orders/{orderId}`)* | Yes. Every control-plane query and mutation is scoped by the organization resolved from verified token claims, never from a request parameter or the request body — a caller cannot reach another organization's API by supplying its id. |
| Is case sensitivity consistently enforced for user identities and role checks during authorization and other validations? | NOT ANSWERED — not established in the inputs for this feature specifically; this is inherited from the platform's existing identity/authorization layer, which this feature does not change. |
| **Cross-Tenant Isolation:** Does the feature strictly enforce tenant boundaries? (e.g., preventing Tenant A from accessing Tenant B resources) | Yes — same mechanism as the resource-ownership check above; organization scoping is enforced at the data-access layer, not only at the API boundary. |
| **Mass Assignment Protection:** Are strict DTOs / whitelists used to prevent users from submitting unintended fields (e.g., `is_admin: true`)? | NOT ANSWERED — whether the create/update request shape is an explicit field allowlist is not established in the inputs; this should be confirmed against the platform's existing request-shape pattern for the equivalent GraphQL resource. |
| **User Input & Web Protection** |  |

The console's test console and the developer-portal's try-it feature both render message content received from a connected counterparty — this is counterparty-supplied data displayed in the UI, and it must go through the same contextual output encoding already applied to every other rendered value in these portals. |
